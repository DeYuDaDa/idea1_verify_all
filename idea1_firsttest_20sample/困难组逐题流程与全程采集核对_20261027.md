日期：2026-10-27。本轮先把题目流程展开，供核对后实现。本文不是已生成的数据，不报告新服务器已经运行成功，也不替代每个新实例的实际前后状态。

依据是用户提供的《视觉事件选择性更新_证据审查与困难题设计_20261026.md》及《机制验证.md》，并结合第41、42步的回测边界。代码中的 `hard_group_plan.json` 还是早期 A–E 条件计划，不能直接当成这里 H01–H05 的生成规格。

本轮只准备数据与人工审核材料，不安装或调用 Qwen，也不运行模型评测。Windows 仍只编辑和审查文件。用户要求先确认逐题流程，因此本轮不修改原有生成器，不启动场景构造。

## 先说明三个容易混淆的边界

1. “目标事件”只有每题最后指定的那一次放入、拾取或开机。此前的拿起、放下、装水、倒空、关门、等待都是历史，必须完整记录，不能藏在 setup 里。
2. 下文的结局是设计预期。真正答案来自新实例的成功动作、事件前状态和规定观察窗口内的实际结果；实际没发生，就不能照表写 Gold。
3. 全部原生步骤都会保存在审计轨迹中；模型输入仍遵守原设计的 V/E/T/S 信息边界。完整保存不等于把隐藏 metadata、坐标、状态差异和后果答案都交给模型。

当前可以据已有机制开始尝试 H01、H02、H03、H04-1/2/3 和 H05。H01 的两只 Mug、H02 的第二个盘子及复杂摆位仍需本次库存与构造验收。H04-4 的改接仍未验证，单独保留，不强行凑齐20题。

## 通用执行方式

每题独立 reset，固定本题对象身份、场景和布局，不把上一题已经加热、装液或拾取后的状态带到下一题。

正式公开历史开始前，可以做房间与资产检查、相机校准以及初态布置。这些也保存，但标为“准备/校准，仅供审核”。公开历史开始以后，为完成故事所做的全部操作都进入历史轨迹，不能把失败尝试和额外状态修改删掉后拼出一段成功故事。

文中的“把物品从甲移到乙”通常展开为：确认物品当时在甲处；原生拿起；确认手中确实是该物；原生放到乙处；确认放置成功；检查实际关系和稳定性。每个原生步骤都有记录和画面。若目标表面不接受该原生动作，保留失败，不把直接改位置包装成成功的搬运。

`Fill`、`Empty` 也必须落实到真实调用。已有液体设置接口使用 `FillObjectWithLiquid` / `EmptyLiquidFromObject`，它们不等于拍到了自然倒水或倒空的动作动画。若前后液体状态在图中可辨，可作为状态变化证据；若不可辨，V 条件不能仅凭成功回执宣布可答。准确动作转录可进入另列的 T 条件，但不能悄悄加入 V 来补线索。

## H01：两个杯子的液体历史交错

### 场景与共同安排

使用两只实际存在、可稳定辨认的 Mug，称为 A、B；咖啡机称为 M。两只杯子开始都为空，分别在机器外的固定停放位。停放位与咖啡机接液区域分开，不能因为杯子靠近机器而提前接到咖啡。

两只杯子不能仅靠隐藏 objectId 区分。优先使用外观可分的实际实例；若外观相同，必须用明确的初始身份和不中断的持取、放置过程建立对应。没有两只可用杯子，就将双杯版本记为未构造；单杯 F6 可以另作低难控制，不能冒充双杯困难题。

我的具体安排是：液体历史期间让机器关闭，两只杯子都不进入机器；历史结束后开启机器，再拿起本题目标杯，最后将它放进机器。原文只规定目标事件发生时机器已经开启，这里把开启时机明确化，以避免历史阶段自动注液。

最终拿起目标杯属于历史，真正目标事件只算原生 `PutObject`。因此目标放入前一刻，目标杯在手中，另一只杯子仍在机器外；不能把它们都写成仍放在停放位。

### H01-1：A最后为空，B最后有水，把A放进机器

1. 展示 A、B 均空，建立两只杯子的身份和固定停放位。
2. 给 A 装水，核对 A 从空变为有水。
3. 给 B 装水，此时两杯都有水。
4. 倒空 A，此时 A 空、B 有水。
5. 倒空 B，此时两杯都空。
6. 再给 B 装水，最终历史状态是 A 空、B 有水。
7. 开启 M；拿起 A，确认没有拿错 B，且 A 在持取后仍为空。
8. 【目标事件】把 A 放入 M，保留该次动作的实际成功回执与观察窗口。
9. 预期：A 变成咖啡，B 保留水；A 在机器中，B 留在外部停放位，M 保持开启。

这里需要同时看出“进入机器的空杯应改变”和“旁边已有水的另一杯应保持”。

### H01-2：A最后有水，B最后为空，仍把A放进机器

1. 独立 reset，重新建立 A、B 均空的初态和身份。
2. 给 B 装水，再给 A 装水，此时两杯都有水。
3. 倒空 B，再倒空 A，此时两杯又都空。
4. 再给 A 装水，最终是 A 有水、B 空。
5. 开启 M；拿起 A，确认 A 的水没有在准备过程中消失。
6. 【目标事件】把 A 放入 M。
7. 预期：A 保留水，B 保持为空。放入成功只改变 A 的位置，不应该把水改成咖啡，也不应该让 B 远程获得咖啡。

### H01-3：A最后有水，B最后为空，把B放进机器

1. 独立 reset，两杯均空。
2. 给 B 装水，再给 A 装水。
3. 倒空 B，再倒空 A。
4. 再给 A 装水，得到 A 有水、B 空。
5. 开启 M；拿起 B，确认 B 仍为空。
6. 【目标事件】把 B 放入 M。
7. 预期：B 变成咖啡，A 保留水。它是 H01-1 的身份镜像，不能因为目标换成 B 就更换规则或问题顺序。

### H01-4：A最后为空，B最后有水，把B放进机器

1. 独立 reset，两杯均空。
2. 给 A 装水，再给 B 装水。
3. 倒空 A，再倒空 B。
4. 再给 B 装水，得到 A 空、B 有水。
5. 开启 M；拿起 B，确认水状态仍成立。
6. 【目标事件】把 B 放入 M。
7. 预期：B 保留水，A 保持为空。这是 H01-2 的身份镜像。

四题固定询问 A 的液体、B 的液体、A/B 的当前位置或容器、M 的开关。液体使用 Empty/Water/Coffee；位置使用经本实例验证的语义位置，不要求模型猜坐标，不把全部祖先关系列表当作直接容器。

## H02：先改苹果的承载者，再交换两个空盘的位置

### 场景与共同历史

使用原成功盘子 P、另一个自然存在且可用的盘子 Q，以及一个苹果 X。初态 P 在左侧停放位、Q 在右侧停放位，X 在 P 上。“P/Q”表示初始建立的物体身份，不是始终表示左盘、右盘。

另留两个稳定位置：苹果暂存台面、空盘周转位。它们不得是另一只盘子，也不能占据稍后需要放置的目标区域。

共同历史按以下完整顺序执行：

1. 把 X 从 P 移到 Q。
2. 把 X 从 Q 移回 P。
3. 再把 X 从 P 移到苹果暂存台面。原文从“移回P”跳到“苹果已经在台面”省略了这一步；这里补出，不删去原文的移回 P。
4. 确认 P、Q 都空，X 稳定留在暂存台面。
5. 把 P 从左侧移到空盘周转位。
6. 把 Q 从右侧移到原来的左侧停放位。
7. 把 P 从周转位移到原来的右侧停放位。至此两盘交换了空间位置，P 在右、Q 在左。
8. 根据具体题目，把 X 从暂存台面放到 P 或 Q。检查成功和稳定性，不能只看一个 Put 回执。
9. 【目标事件】只拿起本题指定的一只盘子，随后观察苹果和另一只盘子的位置。

这段历史中所有搬运都实际执行并保存。不能用坐标重命名 P/Q，也不能在苹果仍放在盘上时直接交换两盘，造成未经设计的提前随动。

### H02-1：最后把苹果放在P上，再拿起P

执行上述完整历史。第8步将 X 放到已经位于右侧的 P 上；Q 留在左侧且为空。确认 X 由 P 承载后，目标事件拿起 P。预期 P 与 X 都离开各自目标事件前的世界位置，Q 不动。

### H02-2：最后把苹果放在Q上，但拿起P

执行同样的完整历史。第8步将 X 放到已经位于左侧的 Q 上，P 在右侧为空。目标事件仍拿起 P。预期只有 P 移动，X 与 Q 都保持原位。

### H02-3：最后把苹果放在Q上，再拿起Q

执行同样的完整历史。第8步将 X 放到左侧 Q 上，P 在右侧为空。目标事件改为拿起 Q。预期 Q 与 X 移动，P 保持原位。

### H02-4：最后把苹果放在P上，但拿起Q

执行同样的完整历史。第8步将 X 放到右侧 P 上，Q 在左侧为空。目标事件拿起 Q。预期只有 Q 移动，P 与 X 都保持原位。

四题都询问 P、Q、X 是否离开目标事件前的世界位置。只有独立承载关系证据可靠时，再问 X 是否仍由原承载者承载；不因拾取后的 parent 字段缺失而生成关系解除答案。

第二盘无法建立时，只能另列“盘子与固定台面”的较低范围版本，不能将其标成已完成上述空盘交换题。

## H03：容器换位后，按旋钮当前控制的炉头选择性加热

### 场景与共同历史

使用 FloorPlan2 已校准路线中的两个炉头 BA、BB，分别由 KA、KB 控制；实际旋钮—炉头映射取本实例核验结果，不按名字后缀或左右位置猜。使用经校准的水壶 X 和锅 Y，不能假定所有可放置容器都有相同受热边界。

初态是 X 在 BA、Y 在 BB，两者均为室温，所有相关炉头关闭。控制映射作为统一机制说明或独立演示提供给模型。温度不可从普通 RGB 直接读取，初态室温必须有明确公开依据。

共同历史是“交换一次，再恢复一次”：

1. 全部热源保持关闭。
2. 将 X 暂放到外部稳定周转位，把 Y 从 BB 移到 BA，再把 X 放到 BB，完成第一次交换。
3. 将 Y 暂放到周转位，把 X 从 BB 移回 BA，再把 Y 放回 BB，恢复原布局。
4. 原布局题到此结束；交换布局题再做一次第2步的换位。
5. 检查实际接触/作用位置、手中无物、两容器仍为室温、所有炉头仍关闭。
6. 【目标事件】只开启本题指定的一个旋钮，随后在与校准一致的窗口观察，不能拍完图才临时延长到想要的结果。

具体搬运必须通过实际合法的动作实现。若某个炉头不是可接受 Put 的目的地，需要依据本实例校准的合法摆放路径构造；不能用成功的坐标设置替代模型应看到的换位历史。

### H03-1：恢复原布局，开启KA

完成一次交换和一次恢复，最终 X 在 BA、Y 在 BB。目标事件打开 KA。预期 KA 和 BA 开启，BB 保持关闭；X 变热、Y 保持室温；两容器位置不改变。

### H03-2：最后再次交换，开启KA

完成一次交换和恢复后，再交换一次，最终 X 在 BB、Y 在 BA。目标事件仍打开 KA。预期 BA 开启、BB 关闭；这次变热的是 Y，X 保持室温。不能仍按初始 X 在 BA 的历史回答。

### H03-3：恢复原布局，开启KB

完成一次交换和恢复，最终 X 在 BA、Y 在 BB。目标事件打开 KB。预期 BB 开启、BA 关闭；Y 变热、X 保持室温。

### H03-4：最后再次交换，开启KB

完成一次交换和恢复后，再交换一次，最终 X 在 BB、Y 在 BA。目标事件打开 KB。预期 BB 开启、BA 关闭；X 变热、Y 保持室温。

每题固定询问目标旋钮开关、BA/BB 开关、X/Y 温度、X/Y 当前承载位置，共7项。另一容器是否保持室温仍以本次真实运行为准；FloorPlan1 中曾出现两容器同时变热的配置，不拿来套用本组答案。

原布局与交换布局的上述实现相差一次换位，属于原稿的具体化方案，并不冒充历史长度严格匹配的因果对照。后续若比较这两个条件的难度，需要另作时长/操作预算匹配，不能给原布局随意插入开火等改变属性的“填充动作”。

## H04：完整嵌套、移出与改接

### 场景与共同安排

沿用已经成功的 Plate P、Bowl B、Apple X 组合及其具体场景路径，不把另一场景的可摆放性自动外推过来。外盘先稳定放好，再将碗放到盘上，最后把苹果放进碗，逐条核对和等待稳定。

初态展示完整嵌套：B 在 P 上，X 在 B 中。另选原始盘区外的稳定台面作为移出位置。所有题最后都只拿起 P，不能在最后同时手动移动 B 或 X。

以下只对实际位移结果作判断，不声称引擎只沿一条唯一的“盘→碗→苹果”路径传播。

### H04-1：把苹果移出再放回，最后拿起外盘

1. 展示完整嵌套初态。
2. 从 B 中拿出 X，放到外部稳定台面，确认它暂时与 B/P 分离。
3. 再把同一个 X 放回同一个 B，确认 B 仍在 P 上，X 确实回到 B 中并稳定。
4. 【目标事件】拿起 P。
5. 预期 P、B、X 均移动；不能沿用中间“苹果已移出”的过时状态。

这里选择“苹果移出再放回”来落实原稿的“一次移出与恢复”。已有完整嵌套正例不等于这条新增历史路径已经构造成功；本次仍需验收放回操作。

### H04-2：苹果移出后不放回，最后拿起外盘

1. 独立建立完整嵌套初态。
2. 把 X 从 B 中移到远处稳定台面，不再放回。
3. 确认 B 仍在 P 上，X 已不受 P/B 承载。
4. 【目标事件】拿起 P。
5. 预期 P、B 移动，X 保持原位。

### H04-3：碗带苹果整体移出，最后拿起空外盘

1. 独立建立完整嵌套初态。
2. 拿起 B，让 X 随碗一起离开 P；把 B 放到已经验收的外部台面。
3. 确认 X 仍在 B 中，B/X 都与 P 分离，手中无物。
4. 【目标事件】拿起空的 P。
5. 预期只有 P 移动，B、X 保持原位。移走整个碗不应被解释为苹果与碗的内部关系也解除。

### H04-4：碗移走，苹果改放外盘，再拿起外盘【待验证】

1. 独立建立完整嵌套初态。
2. 将 B 连同 X 移到外部台面，确认仍保持 X 在 B 中。
3. 从 B 中拿出 X，尝试把它直接放到已经空出的 P 上。
4. 只有实际放置成功、X 稳定由 P 承载、B 留在外部台面且手中无物时，才进入目标事件。
5. 【目标事件】拿起 P。
6. 条件性预期：P、X 移动，B 保持原位。这次苹果移动依赖改接后的当前承载，不能因为碗离开外盘就一律阻断。

第42步恰好在第3步原生放置失败，未执行最后拾取。因此本题当前只有设计，没有被测成功后果。新实例仍失败就保留失败，不改用坐标瞬移、不换苹果、不删除失败后重新拼接故事。

每题至少询问三个对象的世界位移。X/B、B/P 关系及 X 的直接承载者，只在有独立判据时纳入；引擎提供的祖先列表和拾取后缺失字段不能直接充当这些关系的 Gold。

## H05：同一颗土豆，历史熟度与当前炉内外位置交叉

### 场景与共同安排

每题使用一颗实际存在的土豆 Z，独立 reset。微波炉外选两个已规划的位置：自然冷却位置 C、最终炉外校准点 E；若同一稳定台面有两个安全位置，可以同面分区。新 E 必须验收，不能把任意炉外位置当作已校准负例。

两条历史分开：

- 未熟历史：微波炉关闭时放入 Z，再取出，随后放到本题最后位置。准备阶段绝不加热，不能用逆向烹饪恢复未熟。
- 已熟历史：真实放入并关闭炉门，真实开机加热，确认土豆变熟；关机、开门、取到 C，自然冷却到室温，熟度仍保持；之后再放到本题最后位置。禁止用 CookObject 或温度赋值代替这段历史。

在最终目标事件之前，四题都必须实际达到室温、微波炉关闭且门已关好，手中无物。关门属于历史，最终目标事件只有开机。

RGB 不能直接证明自然冷却已经达到某个温度档。我的输入具体化建议是：四题统一公开“最终测试阶段的室温基线已经确认”，但不直接给出土豆当前熟度或炉内外位置；后两项仍从历史恢复。该版本明确称为“温度基线事实+视觉历史+机制规则”，不能称纯RGB。这一信息安排需与本轮题目流程一起核对。

### H05-1：保持未熟历史，最后放回炉内，再开机

1. reset 后确认 Z 未熟、室温，微波炉关闭。
2. 开门，把 Z 放入关闭的微波炉。
3. 再取出 Z，放到外部历史停放位；全程不启动设备。
4. 把 Z 放回炉内，关闭炉门，确认温度仍为室温、熟度仍为 false。
5. 【目标事件】开启微波炉，在已校准窗口观察。
6. 预期温度变 Hot，熟度 false→true，Z 仍在炉内。

### H05-2：真实熟化并冷却，最后放回炉内，再开机

1. reset 后从未熟土豆开始，放入微波炉、关门、真实开机。
2. 确认已经受热且熟度 true；随后关机、开门，将 Z 取到 C。
3. 自然等待到实际温度为 RoomTemp，保存完整等待轨迹，确认熟度没有回到 false。
4. 把 Z 放回炉内，关闭炉门；再次确认室温、已熟和位置。
5. 【目标事件】重新开启微波炉。
6. 预期温度变 Hot，但熟度 true 保持。最终仍熟不是又发生了一次事实值改变。

### H05-3：保持未熟历史，最后留在炉外，再开机

1. reset 后从未熟、室温土豆开始。
2. 在微波炉关闭时开门，将 Z 放入，再取出。
3. 将 Z 放到最终炉外校准点 E，而非放回炉内；关闭炉门。
4. 确认 Z 仍未熟、室温，位于 E，设备仍关闭。
5. 【目标事件】开启微波炉。
6. 预期 Z 仍 RoomTemp、熟度 false，位置保持。不能沿用它历史上曾在炉内的关系而把它加热或煮熟。

### H05-4：真实熟化并冷却，最后留在炉外，再开机

1. reset 后把 Z 放入微波炉，关门、真实开机，确认它已经熟化。
2. 关机、开门，把 Z 取到 C；自然冷却至实际室温，熟度继续为 true。
3. 将 Z 从 C 放到最终炉外校准点 E，关闭炉门，确认位置、室温和已熟均成立。
4. 【目标事件】开启微波炉。
5. 预期 Z 仍为 RoomTemp、已熟 true，位置保持。离开热源不应撤销此前已经成立的熟度。

四题固定询问设备开关、Z 的温度、熟度及当前位置。延续 R2 已记录的有限观察窗口作为起点；新相机与新历史会影响运行节奏，仍需记录真实时间与逐步状态，不能把120次Pass写成固定秒数。

## 每组如何先摆物品，再安排相机

不先写一组猜测的绝对坐标。先确定场景、真实对象和各个空间槽，再用实时位置、包围盒、相机参数提出视点。视点应覆盖故事中的位置变化范围，包括手持位置，而非只对准初态中心。

| 组别 | 先规划的物品位置和运动范围 | 主视角必须说明什么 | 必要时补充的固定视角 |
|---|---|---|---|
| H01 | 机器接杯位、A/B 外部停放位、拿起杯子的手持范围 | 两杯身份、被操作的是哪一杯、目标杯进入机器，另一杯仍在外部 | 对杯口的斜上方细节视角，用于验收空/水变化；目标事件后不额外追拍答案特写 |
| H02 | 两盘左右停放位、空盘周转位、苹果暂存位、拿盘后的携带范围 | P/Q 身份如何交换位置、苹果当前跟谁在一起 | 高位或侧上方关系视角；必要时固定手持区视角，不能拿起后对象出画就宣布无变化 |
| H03 | 两个实际炉头接触位、容器周转位、旋钮和手持范围 | 控制映射、两容器最后在哪个炉头、最后开的是哪一个旋钮 | 炉台近景与旋钮正面两个互补视角；不能用模糊远景猜开关 |
| H04 | 原外盘区、外部移出区、两区之间的持取范围 | 碗/苹果移出或恢复的顺序，最后拾取外盘时各对象在哪 | 原盘区俯斜视角与外部台面视角；若单一远景令苹果只剩少量像素，改用互补视角而非无限拉远 |
| H05 | 微波炉内放置点、炉门开合范围、冷却位C、校准点E | 土豆进出、开关/关门次序、最后位于炉内还是炉外 | 门外向内的合法开门视角和外部台面视角；门关闭后的遮挡是正常状态，不加透视相机 |

模型看到的互补视角，必须按“同一步的一组画面”标识，不能让它们看起来像先后发生的两个物理事件。

### 预检分两层，避免假装没启动就知道房间真实几何

**第一层：启动前的计划检查。** 根据本文件建立角色—位置—动作表，检查物品数量要求、能力要求、每次拿起前手是否为空、放置位是否被占、交换时是否需要周转位、热源是否始终满足历史约束、目标事件是否唯一、查询前提是否有公开来源。这部分不依赖启动 Unity，可检查计划本身是否自相矛盾。本文已把 H02 暂存动作、H03 空位周转、H05 两条历史分开写清。

本轮已人工逐步推演以下位置占用关系；这里只证明安排逻辑上没有要求同一时刻占据同一个满载位置，不证明原生 Put 在真实几何中一定成功：

| 组别 | 纸面推演已经检查的事情 | 仍须在新实例检查的事情 |
|---|---|---|
| H01 | 另一杯始终有独立外部停放位，最后机器只接一杯；最后一次拿起在目标 Put 之前 | 两只 Mug 库存、外部位置确实不触发注液、持取不破坏液体状态、液体可辨性 |
| H02 | 苹果先离开两盘；P 先让出左位，Q 才进左位；P 最后进入已被Q让出的右位；周转位可依次释放 | 第二盘与暂存位可用性、盘子占地与碰撞、苹果放置、两盘和手持苹果的身份连续性 |
| H03 | 每次先用空周转位腾出一个炉头，再交换另一物体；恢复时周转位可重复使用；全过程不开热源 | 真实原生放置路径、炉头接触、锅/壶占地、相邻容器的实际热效应 |
| H04 | 外盘先就位再搭嵌套；苹果移出与整碗移出分别有外部位置；改接只在外盘已空后尝试 | 容量、嵌套稳定性、移出后内部关系是否保留、苹果能否原生改放外盘 |
| H05 | 每题只有一颗土豆；未熟历史不启热；已熟历史先关机再取出冷却；最终关门不改变炉外对象归属 | 冷却是否真正到室温、熟度保留、位置E是否仍为有效负例、观察与截图是否改变时间过程 |

**第二层：正式题目历史开始前的实例预检。** Linux 加载房间后，核对真实库存、资产、实际摆放、包围盒和相机。利用这些实时数据计算候选相机，检查必要对象是否入镜、像素是否过小、关键区域是否遮挡、相机是否在墙体/门/物体内部。只看包围盒不能证明没有遮挡；需要实际 RGB 和相机对应的实例 mask。检测到对象不等于能辨认其液体、温度或朝向。

如果还没有本次实际房间几何，就不能在 Unity 启动前确认真实遮挡、颜色或接触效果。这里的“预检通过”是正式历史前的检查，不是宣称完全不用加载场景便能保证取景。

相机的配置或预检若扰动了状态，应 reset 并重新按固定流程搭建，不能沿用受污染初态。既有成功探针只作起点，不修改原有测量保护条件来让本批通过。

## 全程截图、精确去重和动作标注

### 截图范围

从 reset/初始化开始记录，覆盖准备、相机校准、公开初态、全部历史、目标事件和预定观察窗口。每一次真实原生调用都留结果，包括失败、重试、Pass、开门、关门、拿起、放下和相机配置。

每题必须有一张公开初态画面；其后的每个动作记录返回画面。动作前画面引用上一步的实际结果，不为补一张截图额外调用 Pass。若操作被拆成多个真实的移动/旋转步，每个步都保存；若原生接口只给出一次放置后的结果，就不能宣称已经拍到它在空中的全部轨迹。

固定证据相机尽量在公开历史开始前配置好。逐步采集直接读取每次动作返回 event 中已有的 agent/third-party RGB，不每步调用重规划相机或额外的暂停/恢复。目标 build 是否每种原生动作都返回有效第三方画面，还需首个 Linux 小规模采集验证；当前不能声称已经实测。

若调用异常只留下上一个 last_event，记录为“未取得新画面/引用上一事件”，不能伪装成当前动作的新截图。reset 前后有独立编号，避免 action_index 重新从零开始后串样本。

### 去重方式

对同一相机、同一连续阶段的 RGB 像素计算精确哈希，包含宽、高和颜色模式。只合并连续且完全相同的画面，不做感知近似去重，不丢弃只改变一个小物体的图片。

例如原步骤101至112共12张图片完全一样，审核页显示一张图片，并注明：原有12张、重复11张、覆盖步骤101–112。原始逐步索引仍保留，能还原它对应的全部调用、成功状态和顺序；重复数是张数，不冒充物理时长。

动作或阶段边界不能被去重消掉。同一个PNG可以被“目标事件前”和“目标事件后”分别引用；界面仍保留两处边界。跨阶段即使画面相同，也不把两个语义段合成一个没有边界的缩略图。非连续重复画面可以复用存储文件，但它在时间线上的再次出现必须保留。

### 每题共同的关键标记

- 准备/校准开始与结束，公开历史起点。
- 每次语义操作开始与结束，其内部每次原生步骤及结果。
- 每个历史转折，例如液体倒空、苹果暂存、空盘交换完成、嵌套恢复、冷却结束。
- 目标事件前一刻、目标事件开始、目标动作返回、预定观察窗口结束。
- 原生失败、未取得新画面、前提不满足、相机预检失败、构造停止。

标记与图片分开存储，通过原生步骤号和帧引用绑定。不能只把字烧在PNG上，再把干净模型图与审计图混用。

### 如果整段都是重复画面

先保留动作边界，再分别判断原因：

1. 目标对象从未进入关键视角、或大部分被挡：属于取景/证据失败，不能靠重复数补足。
2. 世界位置明显改变，但相关视角持续完全不变：检查是否出画、读错 camera id、第三方帧未刷新或读到了旧 event。
3. 原生状态改变但 RGB 不可区分，例如液体细节或温度：这不是相机一定坏了；但若这恰好是必须从历史看见的前提，V 条件缺证据，不能自动放行。
4. 对象已经稳定，后面多次 Pass 完全相同：正常合并，保留每步与时间信息。
5. 微波炉关门后看不到土豆，或物体暂时被手持物挡住：按阶段检查。此前已经清楚记录且仍可逻辑确定的条件，不因为当前没看到所有对象就一律判无效。

若正式历史中途必须改相机或重新摆物，不能把失败镜头删掉后接上新镜头。保留该尝试，另起独立的重新构造。避免人为剪接成一条实际上没有连续发生的历史。

## 网页审核需要保留什么

继续使用项目的《一键网页审核.bat》，不改成要求用户手写浏览器命令。

审核页分成两种材料，不能混在一起：

**模型实际待接收的材料：**原题、对象身份约定、全部允许的初态声明、公开历史、统一机制规则、该条件允许的事件说明，以及按顺序排列的全部模型帧。明确标注当前为 V、E、T 或 S，完整保存该版本的待发送文本和图片清单。没有运行模型，就称“待发送输入”，不能称实际调用过的历史请求。

**供审核的完整过程：**所有原生动作、精确动作边界、成功/失败、去重计数、准备/校准段、关键状态检查和对应图片。参考答案与隐藏 metadata 放在可折叠区域；默认先看模型输入，再按需展开诊断资料。

V 条件的图片时间线上可显示“历史片段03/目标事件边界”这类非答案标签，但不能自动把私有动作台账翻译成“给A装水、倒空B”的逐步公开字幕；那会把视觉问题变成文本转录问题。E 只补最后事件的准确说明，T 才给完整可见历史转录，S 给准确事件前状态与最后事件，均不提供目标事件后的答案。

当前网页工具虽然保留完整 model_input，但重建请求时对 history/event 有字段白名单。新题若增加逐步历史、边界或其他公开字段，需要同步检查导出和显示，不能只在源JSON保留、真正呈现时却悄悄丢掉。应以冻结的“待发送文本+帧清单”逐项核验网页显示，不依赖旧 runner 重建新协议。

完整私有采集轨迹也会保存，但不将开头的几何搜索或后来为读答案补拍的画面自动塞进模型序列。模型段从公开初态到预先指定的观察终点，范围事前确定；段内逐步保留，不靠挑好看截图制造连贯性或难度。

## 本轮需要一起核对的具体化选择

这些是原稿未写细、本次补出的实现安排，不是假装原稿已经逐项指定：

1. H01 在液体历史结束后开机，再拿起目标杯；两只杯子必须是实际可用、可辨认的实例。
2. H02 保留 P→Q→P，再补 P→暂存台面，随后交换空盘，最后按题放苹果。
3. H03 通过外部周转位完成原生换位；原布局做交换—恢复，交换布局再多一次交换，因此不声称两段操作数严格相同。
4. H04-1 选择苹果移出再放回碗；H04-4 保持待验证，不绕过失败的原生放置。
5. H05 对四题统一公开室温基线，保留熟度和当前位置的历史恢复难点；这不是纯RGB条件。
6. 每步真实返回画面都保存，连续精确去重后仍保留完整动作映射。完整原生过程仅用于审计；模型输入按协议单独保存并完整显示。
