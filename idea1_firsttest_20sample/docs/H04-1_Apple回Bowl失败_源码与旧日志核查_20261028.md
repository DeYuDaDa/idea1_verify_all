## 最强结论

旧日志与匹配版本源码共同表明：Apple 确实仍是手中同一 Apple，Bowl 仍嵌在 Plate 上；`PutObject` 已通过手持对象、target receptacle 等前置分支，进入以 Bowl 候选点为输入的通用放置流程；是否实际尝试了非空候选列表，旧日志没有直接记录。普通 Apple→Bowl 类型限制已从源码核实为允许，且本动作 `forceAction=true` 会跳过该普通类型检查。agent 到 Bowl 中心约 1.204 m；实体 AABB footprint 的估算上界约 1.34 m，小于默认 1.5 m。由于 receptacle trigger box 未必等于实体 AABB，距离筛除不是首选解释，但当前日志没有实际候选点坐标，不能彻底排除。forceAction 下生成全部点，不按 agent 的视距/视角过滤。`-1` 是 InstantiatePrefabTest.PlaceObjectReceptacle 的 maxPlacementAttempts，表示不限制候选尝试次数。

## 实际动作链与返回分支

Python 端 `Controller.step` 把 action 字典发送给 Unity；动作名 `PutObject` 分派到 `PhysicsRemoteFPSAgentController.PutObject(string objectId, ...)`。关键调用顺序如下（以下行号均是本地 f0825767 源码行号）：

1. `PhysicsRemoteFPSAgentController.cs:4064-4070`：`PutObject(string)` 转给 `PlaceHeldObject(objectId, ..., maxDistance:maxVisibleDistance)`。
2. `:4102-4114`：按 ID 取 target，调用 `placeHeldObject(...)`。带 `forceAction` 时对象检索使用 force 模式。
3. `:4149-4219`：依次校验手中是否有对象、target 是否存在、是否有 Receptacle 属性、必须打开的 receptacle 是否开启、ObjectSpecificReceptacle 的专用类型与容量。失败会用各自的具体错误提前返回。
4. `:4223-4238`：只有 `!forceAction` 时才遍历普通 `PlacementRestrictions`，不允许则报告 `cannot be placed in ...`。本次 forceAction=true，因此该配对检查被跳过；此外 `SimObjType.cs:343-346` 的 Apple 列表本身明确包含 Bowl。
5. `:4240-4257`：forceAction 令 `onlyPointsCloseToAgent=false`；`ReturnAllPoints` 中目标类型也会关闭该限制。之后 `targetReceptacle.ReturnMySpawnPoints(null)` 产生候选点。这里传 null 意味着 `Contains.GetValidSpawnPoints` 不做 agent 距离和 viewport 过滤。
6. `:4258-4286`：如果 seed 非零或 putNearXY，则对已生成点再按 `Vector3.Distance(sp.Point, tmp) < maxDistance` 过滤；此处的 `maxDistance` 就是步骤1传入的 `maxVisibleDistance`，不是后面的 `-1`。非 `putNearXY` 情况按随机种子打乱过滤后的点顺序。
7. `:4288` 调 `InstantiatePrefabTest.PlaceObjectReceptacle(spawnPoints, heldObject, placeStationary, -1, 90, placeUpright)`。第三个参数后面的 `-1` 是 `maxPlacementAttempts`。`InstantiatePrefabTest.cs:165-175` 的停止条件只有 `maxPlacementAttempts > 0` 才生效，所以 -1 表示不因次数上限提前停止；不会参与距离比较。
8. 只有 `InstantiatePrefabTest.PlaceObjectReceptacle` 返回 false 后，`:4292-4294` 才写入 `No valid positions to place object found`。该返回值将“输入点列表为空”和“非空点逐一尝试均失败”合并在一起。

没有“PutObject 的 numPlacementAttempts 参数”。这里有两个不同层级的点数量逻辑：`maxDistance` 筛选候选；`InstantiatePrefabTest.PlaceObjectReceptacle` 的 `maxPlacementAttempts` 限制候选检查数（只有正值时有限制，本次 -1 不限）。

## Spawn points、可见性与物理验证

- `SimObjPhysics.cs:675-705` 聚合各 `ReceptacleTriggerBoxes` 中 `Contains.GetValidSpawnPoints(agent)` 的结果。`:682-686` 仅在 agent 非空时按 agent 距离排序。
- `Contains.cs:221-321` 在每个 receptacle trigger collider 的顶部生成 9×9 网格（gridsize=8）。向下 Raycast 确认可用点；Raycast 命中 receptacle 自身时可加入 hit.point，否则可能加入 trigger box 底部点。传入 agent 时还调用 `narrowDownValidSpawnPoints`（`:324-364`）按相机平面距离 `< maxVisibleDistance` 和 viewport 筛点；本次 PutObject 因 forceAction 对 `ReturnMySpawnPoints` 传 null，绕开这一层按点视距/视角筛除。
- 非零 randomSeed 仍触发 `PhysicsRemoteFPSAgentController.cs:4258-4286` 的二次候选距离过滤，但阈值为 BaseFPSAgentController.cs:290 的 `maxVisibleDistance=1.5f`（除非历史动作显式设置 visibilityDistance；该记录的步骤动作没有此字段）。筛选按照 agent 的 x/z 平面位置与每个 spawn point 的 x/z 平面距离计算，使用点自身的 y 做平面；之后 seed 只 shuffle 候选次序，候选集合不变。
- `InstantiatePrefabTest.cs:137-179`：候选为空立即 false；否则跳过属于 ObjectSpecificReceptacle 的点，对其余点依次 `PlaceObject(...)`，直到成功或全部检查。`-1` 不会打断遍历。
- `InstantiatePrefabTest.cs:240-472`：对每个 candidate，按 90°步长生成角度/底部距离组合。`AlwaysPlaceUpright` 是按待放手持物 Apple 类型决定；Apple 不在该列表，所以会先试 yaw，再扩展到 X/Z 旋转。Bowl 是否出现在该表不决定本动作的手持 Apple 角度策略。每个组合调用 `CheckSpawnArea` 做碰撞检测；通过后检查规定数量的 bounding-box corners 是否处于 receptacle trigger box 内、所有 corners 是否位于 trigger box 上方。注意任一组合若过了 collision 但 corner 数不足或有 corner 不在 trigger box 上方，代码会立即将该 candidate 的 `PlaceObject(...)` 返回 false，**不会继续尝试这个 candidate 的剩余旋转**；只有 `CheckSpawnArea` 返回 false 时才会继续下一个 rotation。`PlaceStationary` 只影响成功后的刚体/父级处理。
- `InstantiatePrefabTest.cs:480-594`：`CheckSpawnArea` 暂时禁用待放对象当前启用的 colliders，暂存原位姿，把对象挪到待测位置计算 bounding box corners；随后将对象恢复原位置与旋转、重开那些 colliders，再用待测 box 的中心/rotation 执行 `Physics.OverlapBox`，检查 `SimObjVisible`、Procedural 与 Agent 图层。它会跳过 agent trigger collider；其它命中 collider 即返回碰撞。由于检测时对象已恢复到原位置，当前手持 Apple 自己的 collider 有可能被 overlap 命中；代码没有在结果中过滤待放对象自己的 collider。是否实际发生取决于 Apple 当前手持位姿和本轮候选位置，现有 metadata 无法判定。日志也没有记录命中对象或哪个 containment corner check 失败。

对比初始化 API：`GetSpawnCoordinatesAboveReceptacle`（PhysicsRemoteFPSAgentController.cs:3423-3476）通过 `FindMySpawnPointsFromTopOfTriggerBox` 生成 21×21 顶部网格；默认可按可见/距离筛点，`anywhere=true` 时返回全部点。接着 `PlaceObjectAtPoint`（`:3178-3212`）按给定坐标直接尝试，不走 `PlaceObjectReceptacle` 的 spawn-point 列表遍历/contained-corners逻辑，但会走 `PlaceObjectAtPoint` 自己的场景范围、对象 bounding box、`CheckSpawnArea` 等规则（`:3215` 后）。因此初始化能通过指定坐标建立 Apple 在 Bowl、Bowl 在 Plate 上的关系，并不能推出后续 PutObject 会采样并接受同一个摆放位置。

## 类型限制与候选假设

普通 `PlacementRestrictions` 在 forceAction 下不执行，所以错误不能归因到普通 Apple→Bowl 类型表拒绝。H04-1 target Bowl 不是专用 ObjectSpecificReceptacle；否则会进入 :4183-4219 的另一套专用槽位处理并给出类型/容量错误，而不是本次通用放置验证错误。`SimObjType.cs:300-301` 将 Bowl 列在 `InReceptaclesThatOnlyCheckBottomFourCorners`，`:313-316` 将 Bowl 列在 `ReturnAllPoints`，`:326-329` 将 Bowl 列在 `AlwaysPlaceUpright`；Bowl 不在 `OnReceptacles`（`:292-294`），也不在严格 8-corner `InReceptacles`（`:286-287`）。Apple 在 PlacementRestrictions 明确允许 Bowl。Bowl 的 `ReturnAllPoints` 强制关闭可见点筛选；`PhysicsRemoteFPSAgentController.cs:4248-4251` 实际按 `handSOP.ObjType`（Apple）判断，而 Apple 不在 upright 列表，故 PlaceObject 会尝试 yaw 及 X/Z 角度组合。源码没有发现 Bowl 嵌在 Plate 上即禁止继续接收内容物的前置禁令。不过，Bowl trigger 区域内实际 collider 可能包括同层或嵌套对象，仍可在物理碰撞与容纳边界检测阶段导致所有点失败。

目前合理的具体候选包括：Bowl 的实际 receptacle trigger/上口几何没有给 Apple 留下通过 containment corner 条件的点；Apple 盒体与 Bowl/Plate/CounterTop 或 agent collider 重叠导致全部 `CheckSpawnArea` 失败；以及以 trigger box 实际坐标计算的候选点与 metadata AABB 推断不同。现有证据不能在这些几何/物理拒绝间作唯一选择，也不能直接断言是底盘碰撞、Plate 碰撞或容器容量。

## 只读调查若要唯一分支需要的最小诊断

无需先改变任务条件；保存一次失败调用的以下值即可确定是哪一层拒绝：

1. `ReturnMySpawnPoints(null)` 原始计数与每点坐标/所属 trigger box；
2. `maxDistance=1.5` 二次过滤前后计数（并记录 agent x/z 与各 point 的平面距离）；
3. 对每个 point：尝试的角度/放置位置、`CheckSpawnArea` 是否命中及 collider 名称/图层；若通过碰撞，再记 `CornerCount`、required corner count 与 `CheckIfPointIsAboveReceptacleTriggerBox` 失败索引；
4. 放置前后 held object ID、Bowl/Plate trigger contents 与 hierarchy。

这些运行时诊断能分开“无 spawn points / 距离筛空 / 全被碰撞拒绝 / 容纳边界拒绝”。在目前证据下，最精确的结论是：失败发生在候选点通用放置验证阶段，具体失败子分支仍未记录。
