## 现有代码为什么不能保证看到装水、倒水

`hard_scenarios.py` 的 `_h01` 确实安排了五次液体变化：A 装水、B 装水、A 倒空、B 倒空、B 再装水。
但循环中的 `_liquid` 只调用 `Interactions.set_liquid`，随后等待一次 Pass。
`set_liquid` 用 `FillObjectWithLiquid` / `EmptyLiquidFromObject` 直接操作指定物体，带 `forceAction=True`。
这条调用链没有在每次操作前接近杯子、拿起杯子、展示杯口、转动手持杯子或安排操作后的证据视角。
所以代码能检查液体字段，却不能保证公开图片里看见变化；仅凭本轮源码也不能断言用户正在看的具体 ZIP 确实执行到了哪一步。

本地对应 AI2-THOR 5.0.0、Unity commit `f0825767cd50d69f666c7f282e54abfe58f1e917` 的源码显示：

- `PhysicsRemoteFPSAgentController.EmptyLiquidFromObject` 直接调用 `Fill.EmptyObject()`，不会替 agent 转动杯子。
- `Fill.Update()` 会在杯子自身向上方向与世界竖直方向夹角大于 90 度、且杯子有液体时调用 `EmptyObject()`。
- `Fill.FillObject` 启用对应液体的渲染对象；`EmptyObject` 关闭这些对象并清空液体字段。

因此，本方案将“倒空”改为真实手持倾斜触发。装水暂时保留原生 `FillObjectWithLiquid`：应看到杯内从无液面变为有液面，但它不包含龙头流水或其他容器向杯中注水的过程。若将来需要后者，那是另一段要单独验证的交互，不把当前接口包装成流水动画。

这里的“固定停放位”表示操作后回到预先声明的对应区域，不承诺每次 PutObject 都恢复完全相同的像素或坐标。程序保存实际位置与承载关系，并用事先设定的区域及稳定性标准判定；不能运行后再放宽范围。若现有接口只能确保同一台面而无法确保可追踪的落点，就明确报告这个缺口。

初态身份框由真实第一视角定位。两杯外观相同的问题仍需人工判定：程序读对 objectId 不等于人或模型能追踪身份。后续默认不向模型添加逐帧隐藏 ID 跟踪框，也不凭私有元数据在遮挡后替模型“认出”杯子。

三个装水阶段都按“拿起—操作—展示—归位”执行，是为了让变化发生在可看见的近处。两次倒水都应有清楚的杯子旋转。AI2-THOR 源码并不保证可见连续水流，本题不要求生成不存在的水流动画；需要看清的是同一杯子的倾倒动作和液体消失。

倾倒过程中可能在一次原生动作的前后直接从有水跳到空，不能伪造一个 simulator 没返回的“正好倒出的一帧”。保存真实返回帧及对应状态即可。持取、导航或扶正若意外清空、重新加水、放错位置或改变另一只杯子的关键事实，应在发生处失败，保留诊断，不继续凑最终状态。

T08 后即刻可能已经是咖啡，不强求一定观察到“放进去但还没变”的中间状态。T09 延用当前 H01 明确的 Pass 0 以及后续 4 次 Pass 窗口并保留实际耗时；Pass 数不等于严格物理秒数。观察中不为看清杯子再次拿起、移动杯子。需要调整相机时保留动作并再查状态，不能把调整后的画面冒充目标动作的即时结果。

若 T09 不符合预期，报告为“本次 H01-1 未达到设计的原生结果”，保留实际状态和图片，不强填咖啡答案、不临时修补世界。这是数据构造失败或机制条件待核查，不是模型更新错误。

## 每个检查点共同保存什么

程序的检查对象是 A、B、M 及其身份、液体、承载关系和持取状态。每个动作至少保存：

1. 检查点编号、实际原生步骤编号、前后阶段、动作参数与成功/失败回执。
2. A/B 的实际 ID、isFilledWithLiquid、fillLiquid、isPickedUp、parentReceptacles、位置与姿态；M 的 isToggled 及实际容纳对象；inventoryObjects。关系需要结合父子双方字段核对，不能只读台面祖先关系。
3. 该动作应该改变的事实，以及同一时段必须保留的另一杯事实、机器状态。既查目标操作是否完成，也查是否误改无关事实。
4. 操作前、操作后即时、归位后/稳定后对应的真实 RGB 和步骤映射。倾倒阶段额外保存全部旋转返回帧，不按普通导航的 1/3 采样丢弃。
5. 图像文件确实存在、来自对应返回事件、没有错误借用上一时刻图像的检查结果。自动杯体可见性作为辅助记录；液面、杯口和身份可追踪性仍交给人审核。

检查不是只在函数结束后读取一次字段。比如 T03 必须保留取杯前有水、取杯后有水、倾倒后为空、扶正后仍空、放回后仍空的整个链条，并在这些时刻核对 B 未变。程序中的“检查项记录”和“失败即停止”要同时实现，不能只调用一个记录 failed 的函数却照常发布。

## 网页上怎样让人对照

网页增加独立的“设计步骤与检查点”清单，按 C01–C04、T01–T09 排列；先展示公开历史，私有校准折叠展示，清楚注明其身份。每个阶段显示：

- 计划做什么、实际走到了哪一步、程序检查通过/失败/未执行。
- 检查的具体事实、期望值和真实值，以及关联的动作回执。
- 可点击的“操作前”“操作后即时”“扶正后”“归位后/窗口结束”等图片链接；图片标题使用同一编号，如 `T03 / A 倒空 / 倾倒后`。
- 程序没有自动判断的项目明确写“需人工审核”：是否看清液面、两杯能否区分、动作是否连贯。程序通过不自动代替人工通过。

debug 模式必须保留上述关键图。相邻图片完全一致时可以共用一个图像文件，但每个检查点都要有独立的时间/步骤引用；不能因去重而吞掉“检查发生过”的记录。多个检查点共用一张图时，网页明确列出这些检查点，而不是捏造变化。

若程序发现关键状态错误，在对应检查点显示失败原因，后续写“未执行”，保留诊断包。若程序状态正确但人看不清液面，则归为“原生状态通过、视觉证据待修复”，不能把两者合并为合格样本。

原生字段、预期答案、程序判断、后续帧的隐藏身份标注均放在私有审核层，不追加到模型图片或文本中。模型实际输入仍是已经明示的初态身份信息、公开规则、实际图片序列和问题。网页可辅助审查，但不能用私有说明补齐模型实际没看到的关键历史。
