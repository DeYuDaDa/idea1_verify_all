运行结束，把 ZIP 和 31 日志放回 Windows 的 `will_not_be_push_to_git/operation_data/`。ZIP 是私有机制诊断包，含完整 metadata、库存和状态，不能作为公开模型输入包。

## 怎样解释运行状态

|状态|含义|
|---|---|
|observed_supported|在本次明确对象、位置、事件顺序和采样窗内，观察符合该探针的局部判据；不代表整个 F 编号普遍成立|
|observed_counterexample|成功执行的测试条件下，出现与该局部待验证命题相反的记录；仍需核查前提和时间混淆|
|inconclusive|没有足够证据区分机制、作用区域、时序或延迟；不是支持，也不是机制不存在|
|setup_unavailable|缺对象/能力/摆放或前置状态无法建立；不算机制反例|
|action_failed|原生动作失败，不能当成成功触发后的结果|
|probe_error|探针实现/兼容性等异常，需要修订代码|

程序退出 0 只表示探测执行过程完成，不等于所有机制成立。异常会保留已完成结果并尽量打包。截图缺失或角度不理想单独记录；原生状态观察不能代替视觉数据质量审核。不同属性的不可适用状态也不能默认为 false。

## 时间和作用范围的限制

Pass 次数与墙钟时间分别记录，不互相替代。F9 包含对固定原生物理步接口的尝试及对照；接口失败或属性计时语义不能确认时保留未知。即使某个物理步接口可用，也不能仅凭动作成功推断所有属性的衰减时钟都与它一致。一个炉头的时间对照不能替代微波炉、清洗、咖啡等其他机制的校准。

F2 的位置或接触探索只对实际成功建立的候选负责。F3 两对象成功不代表三对象已支持。F10 按搬运、加热、清洗分别记录，不能跨机制递推。F11 独立来源、联合来源、撤去一源与无源需有相应证据，短时保持热不能自动当成双来源支持。

物理步接口依据为 AI2-THOR 官方 [Controlling Time 文档](https://ai2thor.allenai.org/ithor/documentation/initialization/)。固定运行 build 为 5.0.0 的 f082576 提交；文档和当前 main 分支不等于已在该 build 上验证。接口可用性仍由本次真实动作结果确认。F9/F11 每个探针结束后重启 controller，避免暂停恢复失败影响其他探针。

`--sample-steps` 调整公共观察器的默认采样序列；针对特定机制的冷却窗、固定 physics-step 对照和扫描臂仍使用其代码中明示的序列，不能将该参数理解为所有探针共用的物理时长。

## 条件困难组

设计文件是项目根目录的 `hard_group_plan.json` 与 `困难组设计与机制依赖.md`。包含 A–E 和可选 F10/F11 扩展；当前均为 conditional_unverified。

拿到本轮结果后，按同 build、真实实例、作用位置、事件顺序、前置状态、时间窗和多对象配置逐项匹配。只观察到某个 F 的一个正例不能自动放行全部组。结构维度包括有效条件、历史修订、对象绑定、属性规则差异、相近边界辨别；实际难度要等模型对照测试，不把更长历史或更多问题直接叫更难。

本轮没有实现/执行困难组数据生成器。先确定原生机制能实现哪些条件，再将被支持的设计翻译成生成代码，Gold 必须来自新场景的真实运行。本轮不要求填旧证据审核表，也不会自动批准坏图进入正式评测。
