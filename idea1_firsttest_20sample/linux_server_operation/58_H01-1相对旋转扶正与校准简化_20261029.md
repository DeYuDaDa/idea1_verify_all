# H01-1 已能自然接水，本轮修复倒水后的扶正

核查包：`20261029T074940Z_hard_groups_20261029T074940Z_GJGb0m_43_hard_groups.zip`。本轮仍只有 H01-1，没有正式题发布，没有运行模型。

## 用户看到的三段分别是什么

1. 第一个候选位置的关水路径试探：移动途中被龙头实体阻挡，原生返回 `Faucet_1000141d is in Object In Hand's Path`，随后退回。
2. 第二个候选位置的关水对照：杯子完成进入水槽下方及退出，没有装水，`dry_control_passed=true`。
3. 第二个候选位置的开水试验：同一杯实际装水；关水并移离后仍有水，`became_water=true`；之后真实倾倒，杯子实际变空。

所以自然接水和倾倒在这一轮已经观察到。未完成的是倾倒后的扶正和归位，不能把本轮说成完整校准已通过。

## 为什么最后报“Water approach lost held/upright cup”

对应构建的 `PhysicsRemoteFPSAgentController.RotateHeldObject(float pitch, float yaw, float roll)` 调用 `AgentHand.transform.Rotate(...)`，参数是相对增量；它与 `RotateHeldObject(Vector3 rotation)` 的绝对设置重载不同。

旧程序先后传入roll 0、20、40、60，实际逐步积累成0、20、60、120度倾斜。原生步骤790时杯子已经空、仍在手中；步骤792再传roll=0，姿态仍为约120度，并没有扶正。

先发生的是 `Cup not restored upright`。旧异常恢复又把这个阶段错误当成接水几何错误，尝试平移仍倾斜的杯子，步骤794随后触发 `Water approach lost held/upright cup`，掩盖了最初的错误。不是杯子被丢掉，也不是装水没成功。

## 改动

- 倾倒使用每次20度的相对增量，逐步记录实际执行成功的增量和实际杯子姿态；超过90度后检查自然清空。不能传一串目标角度来充当增量。
- 扶正按相反顺序执行对应负增量，逐步恢复，最后仍要求原生姿态接近直立、同一杯仍在手中且为空。roll=0不再被当作恢复动作。
- 接水几何试探与接水后的倾倒/恢复明确分阶段。后者失败就保留原始错误停止，不再退回接水搜索，避免二次错误盖住首错。
- 根据用户意见，不再反复执行关水进入/退出对照。优先使用本批次已观察到成功的水槽中心候选，直接进行开水自然接水校准；仍需每只杯子实际接水、离水保水、倒空、扶正、归位。该段属于私有准备，不进入模型的正式历史。
- 关水无效果的旧证据保留在原ZIP，新校准的协议标为 `native_wet_contact_only`，不再声称每次都重跑了关水对照。

mock夹具也修正为相对旋转语义；新增检查要求旋转增量确实正向累计再反向抵消，且恢复错误不会引发接水平移重试。
