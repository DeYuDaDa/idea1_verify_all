## 两只杯子能不能设不同颜色

当前构建对应 AI2-THOR 5.0.0 commit `f0825767cd50d69f666c7f282e54abfe58f1e917`。
对应源码有 `RandomizeColors()`，但这个 action 没有 objectId 或目标颜色参数。
它调用 `ColorChanger.RandomizeColor()`，遍历全场 Renderer 的 `sharedMaterials`，修改材质颜色。
两只从同一实例复制的杯子可能共享材质，因此这个接口不能保证把 A 和 B 分别设成稳定不同的颜色。
`RandomizeMaterials` 也不能直接等同于按 objectId 指定杯身颜色。

本轮没有找到当前构建中可以直接传 `objectId + RGB` 的现成 action。需要稳定的单杯颜色时，应给实例独立材质并增加相应 Unity 支持，或者使用已验证的不同外观资产；这两条尚未在当前构建中实现或验证。
本轮没有启用全场随机变色，也没有把后期加色或逐帧身份标签当作原生 RGB。
现有初态像素框可以说明 A/B 最初是谁，但不能保证它们之后在重叠、遮挡时仍然可区分。H01 的视觉身份可追踪性仍需单独审核。

源码依据：

- `BaseFPSAgentController.cs:779` 的 `RandomizeColors()`；
- `ColorChanger.cs` 的 `RandomizeColor()`，使用 `renderer.sharedMaterials`；
- 两者位于本地只读快照 `主线1/will_not_be_push_to_git/source_audits/ai2thor_5_0_0/repo/unity/Assets/Scripts/`。

## 调试模式怎样减少图片

现在生成默认使用 `--capture-mode debug`：

- 普通移动、转向、抬头低头、变化中的等待画面，约每3步留一张。
- 取放、注水倒水、开关门、开关设备、失败、任务状态变化、阶段边界和最后一帧保留；关键动作的紧邻前帧也保留。
- 连续完全相同的画面仍逐步验证像素相同后合并。不会把原来一张静止等待卡片变成十几张相同卡片。
- 多视角启用时，同一时刻的视角一起保留或一起跳过。
- 每个原生步骤的动作和压缩 metadata 都保存；跳过的图片标为 debug_unsampled，不算重复，也不算图片丢失。

因此图片总量不保证恰为原来的三分之一：关键动作多时会保留更多。调试模式没有保存的画面不能事后恢复，最终需要重新用 full 模式采集并审核。
`run_manifest.json` 和 `trace_index.json` 会记录采样模式；debug 图像用于当前构造排错，不冒充最终连续视觉证据。
