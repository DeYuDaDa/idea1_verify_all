## H01、H02 改了什么

旧实现调用 `CreateObjectAtLocation`，固定 `objectVariation=1`，再试很多位置。
日志显示 Mug 创建返回 `ArgumentOutOfRangeException`；Plate 虽可创建，新增 `Plate|1` 的 `pickupable=true`、`receptacle=false`。
所以不能把问题继续归为“台面位置没挑好”，也不能去掉 receptacle 门槛来让盘子通过。

新实现改成一次 `InitialRandomSpawn`，通过 `numDuplicatesOfType` 请求把所需类型的总数补到 2。
匹配本次 Unity commit 的源码在 `PhysicsSceneManager.cs:542–555` 使用 `Instantiate(original: sop)` 复制场景实例；该路径与旧的 prefab 创建路径不同。最终能否复制出符合功能要求的对象，仍以服务器实测为准。

这个动作会重新放置现有 pickupable，也可能重建 object ID。因此它只发生在公开历史开始前，随后重新绑定角色；不能把旧 ID 与新 ID 的差集当作复制成功的证据。新代码保存全场修改前、动作后和等待后的快照，并检查：

- 原生动作确实成功。
- 当前有足够多不同 ID 的目标对象，而且能力字段满足原来的要求。
- 物体与承载 receptacle 的关系在两边 metadata 中相互对应。
- 三次成功 `Pass` 后，关系仍与动作后的记录一致。

满足这些检查只说明库存补充可用于继续构造，并不说明后续液体、承载、导航或画面已经通过。

## H05 改了什么

H05-3 和 H05-4 的最后一份 metadata 都记录：agent 到台面边界的水平距离约 0.95 米；目标台面 `visible=true`、`isInteractable=true`；但对象基准点距离为 2.187 米。
旧 `_near()` 直接检查 `metadata.distance <= 1.45`，对这种很长的台面不合适。
而且 `_near() and _visible()` 的短路执行导致 `_near()` 不通过时，程序根本没有检查 rendered visibility，却把错误统一写成“Target absent from rendered first-person view”。

新代码只对 CounterTop、DiningTable、KitchenIsland 使用到 AABB 水平边界的距离判断接近程度。
第一视角 rendered mask 的检查继续保留；小物体继续使用原来的距离规则；放置还必须由真实 `PutObject` 和关系检查确认。
AABB 只是接近筛选依据，不是某个位置能成功放下物体的证明。
导航诊断会分别记录 near、rendered_visible、对象基准点距离和边界距离，避免再把两类失败混在一起。
