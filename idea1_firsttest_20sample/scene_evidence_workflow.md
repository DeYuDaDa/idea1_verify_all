# 场景证据规划与复核流程

本文规定从规划到模型盲评的证据关卡。当前脚本只准备和核验人工复核包；它不会自动修复 Unity 渲染，也不会逐状态自动调整相机。证据不足时先阻断样本进入正式评测。需要修改捕获实现时，应在服务器侧完成相应代码审查和复核。

## 状态顺序

`planned → asset/capability calibrated → preconditions/native validate → evidence-camera plan → capture candidate → per-question evidence audit → paired nuisance review → formal approval → model blind`

每一步都要保存对应记录。校准、原生前置条件验证或证据审计失败时，样本留在失败/待复核状态，不得以模型答对来补足证据。模型答案和预测在模型盲评前不能参与决定样本是否保留。

## 先校准，再扩展复杂问题组

先用简单机制控制确认资产能力、状态可观察性和事件前后条件，再建立每个问题到公开历史、规则、事件和 RGB 帧的证据图，并由人工检查。复杂问题组先覆盖“真正变化、条件不满足时不变化、无关事实保留”三类基础对照和证据图审计，通过后才扩展；不规定固定样本条数。不要在基础能力未知时通过增加问题复杂度来掩盖构造或可观察性问题。

规划应逐角色、逐谓词、逐阶段列出必要像素证据和视角，包括校准视角、正面视角、需要时的内部/内容视角、事件前和事件后。设备及其内容若要作为共同可见的负控制，应明确规划该画面。相机代理自身携带的物体与场景物体分开规划，并明确相机约束。可配置的 bbox 阈值只能做可见性合理性检查，不能证明语义可区分。完全相同的 RGB 只作为提示，可能是有意复用；需要结合阶段、视角和证据角色判断。

对每个资产记录 asset ID、build 或资产版本、视角、前置状态和后置状态的可观察性、测试方法及结果。诸如 B19 的预期应写成能力门槛：若没有屏幕特征就拒绝声称可视觉辨认；咖啡与水的视觉区分、初始状态等未知项先标为未知，不能写成已验证事实。

允许根据公开前提、事件和规则推断不可见的结果。隐藏 metadata 只能用于核验真值，不能被放进模型输入当作推理前提；不是把“看不见的后果”全部判无效。

## 问题模式与协议边界

每道问题都必须人工指定一种模式：`direct_visual`、`visual_history_and_rules` 或 `oracle_history_and_rules`。模板默认 `unassigned`，没有自动回退。直接视觉模式必须引用可读且相关的前、后帧，并人工确认状态校准/可区分性。视觉历史与规则模式必须引用提供前提的历史帧、事件和规则；公开文字历史可作为补充，不是必须。Oracle 模式必须引用公开历史事实、规则和事件，只能用于明确声明的 oracle 来源协议，并需说明为何无需视觉校准。

现有公开输入协议目前仍是 oracle 时，应如实保留该来源。查看 RGB、制作证据包或通过审查，不会改变其模型输入历史的来源，也不能据此宣称模型看到了视觉历史。未来若要研究视觉历史，应先明确设计并审核新生成器协议，再运行生成。模板是人工规划材料，当前不由代码自动执行。

## 证据包的人工审查

审查人只使用私有审查包里的公开输入和 RGB 预览；其中不包含 Gold 答案或模型预测。对每道原始问题记录：

- 具体的前置条件、事件证据、目标效果或保留理由；
- 帧、历史事实、规则及事件字段的类型化引用；
- 状态是否可区分、校准依据、图像是否可读且相关、是否存在未解决的视觉/文本冲突；
- 该题的模式、决定和审查说明。

只凭样本级整体判断不够，必须逐题完成。重复帧提示不会自动判失败；审查人要检查它是否符合计划中的视角和阶段。

## Linux 服务器操作

以下命令均在服务器项目目录 `/root/idea1_verify_all/idea1_firsttest_20sample` 执行。先对明确指定的导出根目录生成审查包；脚本不会搜索或选择“最新”导出。

```bash
bash linux_server_operation/28_prepare_evidence_review.sh --export-root /root/autodl-tmp/idea1_firsttest_20sample/exports_scope_v2_20261018T101136Z_wHG53v
```

脚本先在 `thor20` 环境运行 `tests/test_evidence_workflow.py` 的单元检查，再把私有审查目录放入数据盘 `evidence_reviews/`，并将 ZIP 包和运行日志保存到数据盘 `logs/`。将 ZIP 下载给审查人。审查人填写包内 `review_form.json`，保留原文件和公开协议声明。

将完成的表单放回服务器后，显式传入同一导出根目录和表单路径：

```bash
bash linux_server_operation/29_apply_evidence_review.sh \
  --export-root /root/autodl-tmp/idea1_firsttest_20sample/exports_scope_v2_20261018T101136Z_wHG53v \
  --form /root/autodl-tmp/idea1_firsttest_20sample/evidence_reviews/REVIEW_DIR/review_form.json
```

该步骤会重新核验表单与当前公开样本、Gold 指纹及 RGB 指纹匹配，再将获准的完整表单复制到导出根目录的 `evidence_review.json`。它不会覆盖不同的既有文件，也不会代替旧的样本/配对审查。之后仍须对同一个明确根目录运行 `review.py` 的模板/应用命令，完成原来的三项样本与配对检查，再运行 `validate.py --strict`。旧 06 系列脚本默认指向 exports，不可不加检查地用于本轮 exports_scope_v2 根目录。只有新证据复核与旧严格审查都通过后，正式评测才可继续。

准备或复核证据包不需要重跑模型、重新生成数据或运行 Unity。导出数据改变后，旧表单会因指纹不匹配而失败；应为明确的新导出重新准备审查包。
