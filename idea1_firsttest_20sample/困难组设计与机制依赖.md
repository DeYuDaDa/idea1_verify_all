# 困难组设计与机制依赖

## 状态与使用边界

本文和同目录 `hard_group_plan.json` 是**条件性设计**。A–E 组只有在其 `prerequisite_conditions` 所列的精确机制、同 build/asset、事件位置、历史末态和对象数量都由探测记录支持后，才可进入数据构造。当前没有据此生成新数据，也没有证明这些组比现有题更难，更没有证明 frontier 模型会在哪组失败。JSON 中的 `status` 均为 `conditional_unverified`。

gate 应逐组输出探测结果和缺失证据，不能只看某个 F 编号全局通过就放行。比如 F2 在一个 Microwave/Potato 上通过，不代表另一个场景的咖啡机、炉头或水流接触条件也成立；F3 的对象库存也不能替代机制证据。gate 只报告可行性，不创建对象、不自动编造轨迹、不填 Gold。每个正式标签应由该条记录实际执行前后的 metadata、动作成功状态及可审查的公开历史/图像证据推出。

本轮 `mechanism_probe.py` 只实现原生观察与局部结果汇总，**没有实现自动放行困难组的 gate 或困难组生成器**。上文对 gate 的描述是未来实现契约，不是已交付能力。JSON 的 `current_probe_refs` 已将 A–E 及可选扩展对应到本轮真实 case ID；每项还列出当前探针不能替代的控制条件。后文 M01/P20 等旧编号是机制入口和原代码检查的参考，不代表它们已经通过本轮探测。

## 本轮新增的机制探测

|事实|本轮实际测试|仍不能由单次正例推出的内容|
|---|---|---|
|F1|Toaster、Microwave、CoffeeMachine 各自的先放入后开源、先开源后放入|设备之间的触发顺序不互相代替；动作拒绝不算成功触发|
|F2|Microwave 内/外固定对照，Microwave 与 SinkBasin 原生位置的中心/边缘候选扫描|候选名不等于真实作用边界；未获得不同关系/效果时保留未知|
|F3|Toaster、Microwave、水流、炉头的单/多对象尝试，炉头另有 Pot/Kettle 单独控制|真实库存、逐实例独立控制、三对象同时成立都需另匹配；多对象局部效果不等于独立性|
|F4|已熟/未熟 Potato 加热、移出、自然冷却并追踪熟度|短窗没冷却不代表永不冷却；初态设置动作不当成自然热机制证据|
|F5|脏/净 × 空/有水四格，每格有开水/关水对照|最后事件前的四格基线需实际成立；SinkBasin 关系不能代替水流接触|
|F6|空杯、有水杯、先装后倒空、先空后装水四种咖啡机放入条件|最终液体/温度按实测；一个状态保持不证明所有液体都保持|
|F7|移出、取出后放回、一直保留；Pickup 后对比位移向量和相对位置|一个子对象不能证明多子对象独立性；缺 parent 字段不等于失去支持|
|F8|两个旋钮分别开关、交换 Kettle/Pot 位置，核对炉头与两对象温度|metadata 映射只选候选，不能代替真实联动和局部热效果|
|F9|炉头源撤销/继续的固定请求 physics-step 与等动作数观察对照|属性计时仍标未验证，不能全局推广到所有设备或属性|
|F10|嵌套搬运、加热、清洗分别执行并检查嵌套链|搬运成功不证明热/水递归；直接暴露与嵌套还要匹配控制|
|F11|真实双炉头候选共同位置，单源/双源/分别撤源/无源分 reset 观察|几何筛选不是物理作用证据；余热保持不能证明替代支持|

同一物理机制在不同属性或资产上的时间语义不作自动等同。结构复杂度 C4 优先通过同一真实规则下的条件交叉、查询属性选择和保留/变化分布来操控，不擅自修改模拟器规则。若某个对照必须改变查询属性，固定查询数量与输出接口并明确记录变化，不能同时声称完整问题文本也保持不变。

现有开发契约限定此 Windows checkout 用于编辑和 Git 文件管理；本次只写设计 JSON 与说明文档，不运行项目、Python、测试、模拟器、WSL 或环境安装。仓库流程还要求模型可见输入和隐藏评分 metadata 分离；失败构造要保留为失败，不能以预期结果替代观察值。

## 复杂度如何独立操控

对象数、历史长度、问题数只是规模或负担变量，不能直接命名为“难度”。这里分别操控五个结构维度：

|维度|可操作的配对变量|需要锁定的因素|
|---|---|---|
|有效条件组合|只翻转一个已被验证会改变目标属性结果的必要条件|对象实例、事件、查询、其他状态和时长|
|条件的历史修订|相同末态，一边需由操作历史恢复，一边在最后事件前直接给出末态|最终事件、事实值、问题数量、对象与场景|
|条件与对象绑定|保持同一组条件不变，只交换哪个对象具有哪条条件|同类型对象数、属性、历史长度、题数、输出格式|
|事实规则差异|同一对象、同一事件分别查询不同属性；一个属性可变，另一个应保持|目标事件、对象、问题集合与答案接口|
|近边界辨别|正例与负例只差一个必要条件，如接触与邻近、空杯与已有水|其余所有条件与时间|

每个操控都应能被单独移除或翻转。如果删掉某段历史或某个条件不影响任一正确答案，它没有增加本研究关心的结构复杂度。所有配对固定对象实例数、问题数、问题顺序、问题措辞/输出格式和事件步骤；若为了配平而增加 sham 操作，必须先证明该操作不改状态且公开记录。不能把几个维度同时改动的版本叫严格最小对照。

## A–E 候选组

### A：微波炉中的历史状态与对象绑定

目标是分别判断对象在启动时是否仍在有效作用范围、对象当前是否可熟化、以及受热是否改变当前温度和熟度。具体历史应包括：一个 Potato 曾取出后放回，保持未熟且处于室温；一个 Potato 曾受热变熟、取出冷却，再放回；一个 Potato 曾在微波炉内，启动前已取出。最后事件固定为微波炉关闭状态下成功执行 `ToggleObjectOn(Microwave_1)`，且在 freeze 时逐个确认容器关系、初始温度与 `isCooked`。

严格 A/B 对照只交换一个 Potato 的末态容器关系，或单独交换一条熟度历史，不要同一对里既换关系又换属性。逐 Potato 询问当前位置/容器关系、温度和 `isCooked`；设备的 `isToggled` 与 `isOpen` 作为独立检查。条件性预期是：当前在作用范围内且相应机制成立的对象可能改变温度；未熟对象是否熟化必须由同 build 的探测决定；曾经已熟且再次加热后最终仍为 `true` 是正确的事实保留，即使更新操作标签可能不同。特别是，**“已熟对象再加热后最终仍为 true”不是 over-propagation 造成的事实值错误**。只有最终值被错误改成 false 才是熟度事实错误；“报告发生了新变化”应另列为操作分类错误，不进入事实值主指标。

库存必须先于设计确认。当前 `generator.py` 的 M01 只选取一个 `Potato_1`，再加一个 Bowl；这不能支撑“三个 Potato”样本。不得克隆 Potato、假定场景有多个 Potato，或以 Bowl/Bread 替代后仍声称同类对象绑定。需在相同 build/asset 中证明至少三个真实、可独立校准的 cookable Potato 实例同时可用。库存不足时，多对象组标 blocked；可留下单 Potato 的 inside/outside 最小对照，并明确 C3 对象绑定没有被测试。

放行依赖 F1、F2、F3、F4、F9：对照 `specs.json` 的 M01（动作成功和开关变化；外部 Potato 是否仅因同场而变化）、M02（事件前后温度及熟度，B 在事件前已熟并保留）、M04（Cup 在启动时的最终 containment 与温度/位置），以及 `generator.py` 中 freeze 后的事件执行。M02 现有逻辑可作为“已熟值保留”的控制，但并未证明过热会造成事实值错误，也没有验证移出热源后的冷却保熟机制；若组依赖该历史，必须新增并命名冷却保留探测。T17 是 toaster 的启动顺序证据，不能代替微波炉顺序证据。

### B：流水机制下的清洁与填充属性交叉

目标是在真实水流接触已成立后，分别问清洁状态和液体填充状态。可行候选状态为：A 脏且空；B 脏且已装水；C 已清洁且空。历史需记录相应脏/净、装水/倒空操作及事件时刻的最终状态。必须先证实 `canFillWithLiquid` 对每个 Bowl 适用、实际水流作用位置与接触、开启状态以及固定等待时长。条件性预期是脏物体可能被清洁、空且可填充的容器可能装水；已清洁/已装水的事实若仍成立只算保留，不是新的变化。

当前 W08、W09、W10 分别以单 Bowl 测 dirty+empty、clean+empty、dirty+water。它们可作为 F5 探测入口，不能据此声称多 Bowl 同时独立反应：`generator.py` 的 `water()` 每对仅选一个目标对象。三 Bowl 版本要求同场景内有三件可辨认实例、每件都能分别放到已核实的水流接触位置，并逐件观察状态。如果水流接触只能对一个对象成立，组应退回单 Bowl 配对。W11 的 Plate 是待验证的 nonfillable 负控制，不是 Bowl 的替代；不可适用的 fill 字段应标 not_applicable，不能强写 false。

严格配对应一次只交换“是否已装水”或“是否已清洁”之一，其余对象、历史、问题数和顺序不变。询问每个对象的 `isDirty`、`canFillWithLiquid` 适用性、`isFilledWithLiquid`、`fillLiquid`，并单独询问位置/容器关系。放行依赖 F2、F3、F5、F9：W08 `running_water_contact_has_native_effect_or_valid_negative`、W08–W10 实际前后属性检查、W11 `nonfillable_negative_control`（仅适用时），加上明确的接触图像/动作证据和等时长关水对照。`SinkBasin` 的 parent 关系本身不等于水流接触。

### C：咖啡机条件与液体历史

这组优先保持一个 Mug 和同一台 CoffeeMachine：事件前机器已经开启，Mug 的历史一边先装水再倒空、最后为空，另一边从空杯历史结束为装水；在 freeze 时确认当前液体值，而后两边都执行成功的 `PutObject(Mug_1, CoffeeMachine_1)`。查询 `isFilledWithLiquid`、`fillLiquid`、温度、容器关系和机器开关，各事实分开。

预期只能条件化表述：若 C13/C14 的真实机制探测确认“开启机器内的空杯”会被注入某液体，则在该条件下检查该属性；已装水 Mug 的结果必须服从实测，不得先验写成咖啡、热或被替换。C14 明确要求 water-filled 结果按模拟器 metadata 处理。液体/温度的事实值与“机制是否适用”分开评分。

严格 A/B 对照只改变事件时的液体状态，保持对象、机器、目标位置、成功事件、问题数和格式不变。C13 提供机器开/关的入口，C14 提供空/水状态对照，C15 提供 inside/nearby 位置边界但它本身标为非严格配对，不应拼成一个严格对照。放行依赖 F1、F6、F9，核对 C13/C14 的前后液体、填充、温度与机器状态检查，并新增配平的历史倒空/装水操作验证。若不能通过历史操作获得可配平末态，就将 C14 保留为直接初态诊断，不宣称历史修订难度。

### D：拾取时把运动变化与承载关系分开

候选组在拾取一个 Plate 时询问每个子对象的世界位置是否变化；若并且仅若承载关系可独立验证，再额外询问其相对于 Plate 的关系。历史包括某对象被取下后放回、某对象被移到附近台面、某对象保持在 Plate 上。事件固定为成功 `PickupObject(Plate_1)`。严格配对只交换一个子对象在 freeze 时的承载条件，确认其他对象位置、相机观察和 settling 时间相同。

位置变化和承载关系是两个独立结果：支持对象随 Plate 移动可以由 before/after 世界坐标检验；不能因为它动了就推断 after 仍有 parent 关系。尤其当前 P20 已明确：`apple_support_at_frozen_before` 检查拾取前关系，`apple_carrying_boundary` 检查 Apple 是否实际位移，而 `post_pickup_apple_parents_audit_only` 的 `used_as_support_gold` 为 false。AI2-THOR 在拾取后省略子对象 `parentReceptacles` 时，不能把字段缺失直接写成承载关系断开或关系 Gold。要评分支持关系，必须有独立校准的物理/图像依据；没有就从模型题中删去该 Gold 查询，只保留位置变化题。

当前 P20 每变体只有一只 Apple。多对象版本需同一 build/asset 中有三个独立子对象并分别验证支持、位移和邻近负例；对象类型不同时还须把类型在支持/非支持条件间平衡。库存不足时退回单 Apple 运动边界控制，不声称对象绑定复杂度。依赖 F3、F7、F9，并以 P20 的上述精确 named checks、成功状态、坐标阈值、无拾取等时长对照作门槛。

### E：炉头映射与物体位置的交叉

先由原生 `controlledObjects` 映射证实 Knob 到 Burner 的关系，并在公开历史/规则中给模型可用映射；映射不能靠 A/B 名称或 suffix 猜测。之后让两件已校准对象在两个有效炉头之间有明确位置历史，最后只打开一个已映射的旋钮。每个对象分别询问位置、接触/承载关系（仅在可独立观察时）、温度；每个 Knob 和 Burner 的开关状态也单独询问。

配对时固定同一映射、旋钮、对象数/类型、问题顺序与事件，只交换两对象最终炉头位置之一项。条件性温度预期必须等映射、接触和实际加热都通过后才可启用。S05 的 Kettle 在 A/B 炉头位置与实际映射是位置边界入口；S06 是 active burner 的接触 vs nearby 入口；S07 改事件目标 knob，是非严格目标身份对照，不是“只交换当前对象位置”的严格对照。当前三对都只用一个 Kettle；多对象版须核对两件自然存在、同类型或类型平衡的可加热对象，不能克隆 Kettle 或把不兼容对象当等价替代。

依赖 F2、F3、F8、F9。重点核对 generator 的 `two_distinct_native_stove_control_mappings`、`two_independent_control_targets`，S05/S07 实际 knob/burner 检查，S06 的温度与支撑/接触检查，并增加原映射复测、目标 knob 激活、等时长不激活对照。机制映射若因场景不同而改变，必须以该实例记录为准并在模型可见输入中明确，不能把别的场景映射复用为 Gold。

## A–E 原建议的调整理由

早期表格里的 A–E 是候选例子，不是现成事实。此版保留研究问题、收窄主张并增加了阻断条件：

- A 保留微波炉与历史关系/属性交叉，但加入三 Potato 库存门槛和单对象 fallback；原提案把三个同类对象当作可直接安排的事实，现有生成器只选择一个 Potato。另将“已熟再加热”明确为值保留控制，避免把最终仍为 true 说成事实级 over-propagation。
- B 将“多对象水流”写成有待验证的能力，不从三个单 Bowl 条件样本外推多对象同时效应；额外要求真实接触和字段适用性。
- C 保留空杯门控，增加历史倒空/装水版本；原建议“已有水则保留”需要遵循真实 metadata，不能先定义模拟器结果。
- D 拆开对象运动与承载关系。`parentReceptacles` 缺失不能直接作为承载关系负 Gold；先通过独立运动/支持对照再决定支持关系能否进入题目。
- E 保留旋钮与位置联合条件，但要求映射由公开规则或历史示范给定；模型不应猜控制关系。当前 S07 的切换目标也不能当成严格位置交换。

## 机制失败、未知与数据生成契约

每个候选组先做机制探测，再产出可执行组 plan。建议流程如下：

1. 对精确 build、scene asset、对象实例、位置/接触区和 event time 运行单机制探测，记录 setup actions、原生动作成功、freeze 状态、后状态、时间步、字段适用性和截图/历史证据引用。
2. 在同一实例上做正、负和边界对照；多对象组逐对象复核，避免单对象结果被扩展为场景级普遍规则。对象库存不足记为资源/构造 blocked，不通过克隆填补。
3. 根据观察结果给 gate 状态：`pass` 只代表列出的 exact prerequisite 对该 asset/build/条件有证据；`fail` 或 `unknown` 都不进入生成。需要时缩小属性、去掉无法审计的问题，或使用 JSON 明列的低范围 fallback。
4. gate 通过后才写具体 variants、历史动作和问题；Gold 从真实 before/after 与公开规则/事件推导，保留 `unknown`/`not_applicable`。如果两边结果没有形成预设差异，样本不能为了符合设计而改标签，应调整条件或 blocked。
5. 对模型盲评的样本，执行既有 scene evidence workflow：逐题引用帧、历史、规则、事件；逐对象审读像素可见性和身份；确认 A/B nuisance 匹配。建审查包、模型回答或预测不能补足机制证据。

“frontier 难”也必须实证：先通过上述机制和证据 gate，再用固定对象/问题/输出格式的配对干预观察模型事实值错误，并把事件识别、条件恢复、对象绑定、属性判断与输出格式错误分开。若某维度的配对错误并未增加，就不能仅凭复杂案例观感称其为有效难度来源。设计阶段不做此结论。
